>zig init
>初始化一个新的 Zig 项目。此命令会在当前目录下创建 build.zig、build.zig.zon 和 src 目录（包含 main.zig 和 root.zig）。

>注意：在 Zig 0.12+ 版本中，原来的 zig init-exe 和 zig init-lib 命令已合并为统一的 zig init 命令。新的模板同时包含一个可供其他项目导入的模块（src/root.zig）和一个可执行文件（src/main.zig），用户可以根据需要删除不需要的部分。

# Zig语法
## 模块导入
@xxx 是编译器内建函数（builtin）

@import("std") 返回的不是“把代码粘贴进来”（C 的 #include 那种文本替换），而是返回一个命名空间（namespace）——一个包含了目标文件所有 pub 声明的 comptime 值。（所谓pub就是public）所以你需要用 const 给它绑个名字，之后通过它访问。
Zig没有全局命名的空间，这是比较微妙的。也就是说你在不同模块中重复命名某个变量，比如都叫foo，那它不会和C一样最后编译进同一个符号池子里面，有点像C++中的包，避免了C中不得不使用gpio_、SDL_ 这种前缀防撞名来避免出现 duplicate symbol 错误。
# Zig编译脚本
Zig的编译系统相当复杂，它实际上把很多细节透露给了开发者，使得我们不得不面对一些CMake或者GCC干掉的事情，为了解决这个问题Zig的选择是强制用户使用一套比较规范的编译脚本写法。
```zig
const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const exe = b.addExecutable(.{
        .name = "zig",
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/main.zig"),
            .target = target,
            .optimize = optimize,
        }),
    });

    b.installArtifact(exe);
}
```
这是一个典型的Zig构建脚本。开头引入了STD标准库，后面是一个build函数，非常自然。  
函数中有若干个常量，他们如下：  
- `b.standardTargetOptions`: 允许构建器读取来自命令行参数的目标配置，并返回可直接传给模块 .target 的 ResolvedTarget。  
- `b.standardOptimizeOption`：允许构建器读取来自命令行参数的构建优化模式。  
- `b.addExecutable`：创建一个 Build.Step.Compile 并返回对应的指针，Zig 0.16 起通常通过 root_module = b.createModule(...) 指定入口模块。  
- `b.path`：该函数会返回相对当前包根目录的 LazyPath，常用于模块的 root_source_file  

build 是构建的入口函数，而不是常见的 main，真正的 main 函数由 Zig 的构建系统提供，这是由于 Zig 的构建分为两个阶段：

配置阶段（configure）：执行 build.zig，生成由 std.Build.Step 构成的有向无环图（DAG，即 Directed Acyclic Graph——一种不包含环路的有向图结构，用于表达步骤之间的依赖关系）
执行阶段（make）：执行真正的构建逻辑。
也就是说，zig的编译流程，包括指定编译目标产物，寻找需要编译的文件，以及真正执行编译，都是一种步骤(Step)，是可以修改顺序和配置的。整个编译文件build.zig,其实可以看成一段bash脚本，它获取一些参数，执行一些命令。每个step就是脚本命令的一环，没有依赖的step之间会并行运行。此外，step内部包含的行为还会被开放到命令行里面，例如你可以`const flash_step = b.step("flash", "烧录到板子");  ` ,这样当你执行 zig build flash，就会直接执行这个step对应的代码及其之后的step代码。  
所谓的Step有向图，其实就是构建过程之间的依赖管理，例如要构建的二进制程序 A 依赖一个库 B，那么我们可以在构建 A 前先构建出 B，而 B 的构建依赖于 另一个程序生成的数据 C，此时我们可以再指定构建库 B 前先构建出数据 C，大致的图如下：
```
数据C
|
C --> B --> A
      |     |
      |     程序A
      |
      库B
```
由于这个过程可以被复用，因此这个流程完成后通常会被当成缓存直接使用，所以通常来说，build函数中应该只涉及关于step相关的内容，不应该加入一些执行程序，即使其作为一段zig代码完全支持这一点。
相对应的，我们应该将其要做的事的函数指针绑定到Step上。每个 Step 结构体里有一个函数指针字段 makeFn，执行阶段图调度器走到这个节点时，就调用它。当然，有些时候某些代码没法用一个函数/进程表示，这种时候Zig
也提供了.custom Step这种语法。这里暂时不展开，之后我可能会把P_RTLog用Zig重写一遍？
最常用的节点方式是，提供一个空的step，其作为名字入口，然后depend到实际工作的step上。zephyr内置了非常多的step模板，例如b.addSystemCommand会添加一个执行命令行的step。这些实际工作性质的节点，即不是显式step声明的，不会出现在命令行的可选项中。也就是入口必须是一个自定义的空step。

# 任务调度
假设我们有一系列原子的任务不能再拆分了，然后作为RTOS的任务/线程去执行。那么，显然会有很多上下文切换负担。但是如果我们随意组合这些任务，又会产生一些问题：不同任务的优先级不一样，有的需要在严格时间内完成，有的只需要在某个时间段完成即可。因此，如何处理原子任务之间的依赖关系，以及优先级，尽可能合并任务，就是操作系统使用者和开发者所需要考虑的一大问题。  
总的来说，这个思路颇类似计组中的微指令，有三条原则：
1. Deadline不能小于总耗时
合并的原子任务里，最紧的 deadline 是 D_min = min(Dᵢ)。合并体的 deadline 不能比这个更松，否则那个最急的任务被拖死。
2. 合并后整体仍然可调度
3. 相位对齐
原子任务 a 原本在时刻 t 到达、t+ε 就能跑；合并后它要等合并体的下一个释放点，最坏多等 T' - ε。这个额外的响应延迟（release jitter）要加进其他依赖它的任务的 RTA 里。如果某个外部任务的 RTA 本来就紧（R ≈ D），加一点 jitter 就爆——这时候合并省下的那点切换开销抵不上 jitter 引入的不可调度性。  

其实本质上，这是把零散任务整合起来批处理的一个过程。在Zephyr中，tickless就用了类似的思想，它先估计睡眠时期需要完成的任务，通过尽可能在醒的时期一次性完成大量工作，同时避免影响任务本身要求的时序。  

这个思想有一个名字：task allocation / task fusion for schedulability。除了Zephyr以外，AUTOSAR OS 的 ScheduleTable、Linux 的 timer coalescing也用了类似的设计。
